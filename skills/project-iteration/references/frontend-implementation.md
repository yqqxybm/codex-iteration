# Frontend Implementation And Verification

Read this reference only when the assigned implementation changes visible UI or
when the Context Packet requires frontend control or verification. Use
`project-frontend` for design judgment; this reference translates its accepted
contract into implementation and closeout boundaries.

## Implementation

A proved `very_small` presentation-only copy replacement is not frontend design
work merely because the literal is rendered in a UI. Otherwise consume and
return the applicable `project-frontend` contract through its canonical
frontend control contract; do not reproduce its field schema or instantiate
inactive checks.

If the Context Packet marks `visual_target_gate: required` for Tier 2/3,
full-page, dashboard/admin/workbench, source-inspired, or high-aesthetic work,
derive or obtain the visual target through `project-frontend` before editing.
Do not implement from style adjectives alone. The selected aesthetic target is
the visible objective, product-state robustness is a hard constraint, and task
or interaction success cannot complete a visible mutation without the holistic
rendered aesthetic verdict. Add visual, motion, layout, or state complexity only
when it serves the Simple-Coherent-Elegant law and the user's workflow.

## Verification

Choose the smallest applicable combination of:

- `browser_smoke`: route/page loads, no fatal console/runtime error, the assigned
  core interaction does not crash, and the checked viewport has no blocking
  overlap or horizontal overflow;
- `visual_qa`: required at the AQ depth selected by `project-frontend` for every
  visible design mutation; only a proved non-visual or presentation-only literal
  change may mark it not applicable;
- `state_pressure_qa`: relevant loading, empty, error, permission, long-content,
  long-list, responsive, localization, or theme states selected by the frontend
  contract;
- `content_copy_qa`: only when content quality or a durable content contract is
  at risk, not merely because a mutable literal changed.

`browser_smoke` is a narrow runtime proof. It does not silently absorb aesthetic
taste, copywriting, real-domain content, design-system fidelity, state matrices,
language review, or sibling-surface inspection from the other subscopes.

Use the canonical frontend-quality contract through `project-frontend`; do not
duplicate or extend its schemas here. Report the focused verification needed to
support the visible objective and relevant states. If a selected state cannot be
verified, the result is blocked or carries a specific residual risk. Strict or
complete frontend verification cannot omit an applicable selected dimension
without a reason.
